# Wrapper 규약

개발자가 자기 앱을 Workflow Auto 에 붙일 때 지켜야 할 최소 약속입니다.
실제로 만드는 방법은 [WRAPPER_PROMPT.md](WRAPPER_PROMPT.md) 를 보세요.

## 왜 이런 게 필요한가

앱이 100개면 오케스트레이터가 100가지 방식으로 앱을 부르는 코드를 갖고 있어야 합니다.
대신 "부르는 방식"을 하나로 정해 두면, 오케스트레이터는 그 하나만 알면 됩니다.
콘센트 모양을 통일하는 것과 같습니다.

그 규격으로 **MCP(Model Context Protocol)** 를 그대로 씁니다. 업계 표준이라
AI 코딩 도구들이 이미 잘 알고 있고, 우리가 규약을 새로 발명할 필요가 없습니다.

## 1. 전송 방식

- **MCP streamable HTTP** 를 씁니다.
- 주소는 보통 `http://<호스트>:<포트>/mcp` 형태입니다.
- 이 주소가 앱스토어에 등록하는 `endpoint` 값입니다.
- 외부 인터넷은 전혀 쓰지 않습니다. MCP 는 서비스가 아니라 통신 규격입니다.

## 2. 반드시 구현해야 하는 것

| MCP 메서드 | 언제 불리나 | 하는 일 |
|---|---|---|
| `initialize` | 접속할 때마다 | 연결 확인 (라이브러리가 자동 처리) |
| `tools/list` | 앱 등록 / 새로고침 시 | 이 앱이 가진 기능 목록을 알려줌 |
| `tools/call` | 오케스트레이터가 일을 시킬 때 | 기능 하나를 실행하고 결과를 돌려줌 |

`mcp` 파이썬 라이브러리의 `FastMCP` 를 쓰면 이 셋은 자동으로 처리됩니다.
개발자는 기능 함수만 쓰면 됩니다.

## 3. 기능(tool) 작성 규칙

```python
@mcp.tool()
def find_employee(employee_id: str) -> dict:
    """사번으로 직원의 이름, 소속팀, 직급, 상위 관리자를 조회합니다.

    Args:
        employee_id: 사번. 예) E1001
    """
    ...
```

- **이름**: 영문 소문자와 `_`. 무엇을 하는지 드러나게.
- **인자 타입 필수**: `str`, `int`, `bool`, `list[str]`, `dict` 등.
  타입이 없으면 오케스트레이터가 무엇을 넣어야 할지 모릅니다.
- **docstring 첫 줄이 가장 중요합니다.** 오케스트레이터는 이 문장만 보고
  "지금 이 기능을 써야 하나?"를 판단합니다. 막연하게 쓰면 안 불립니다.
  - 나쁨: `데이터를 처리합니다`
  - 좋음: `사번으로 직원의 이름, 소속팀, 직급을 조회합니다`
- **Args:** 아래에 인자마다 한국어 설명과 예시를 답니다.
- 반환값은 `str` 또는 `dict` 를 권장합니다. 그대로 사용자에게 보여줄 수 있는
  결과라면 `str`, 다른 앱이 이어받아 쓸 데이터라면 `dict` 가 좋습니다.

### 하지 말아야 할 것

- 파일 맨 위에 `from __future__ import annotations` 를 넣지 마세요.
  인자 타입이 문자열로 바뀌어 MCP 가 읽지 못합니다. (가장 흔한 실수입니다)
- 되돌릴 수 없는 작업(메일 발송, 결재 상신, 삭제)을 확인 없이 실행하는 기능은
  만들지 마세요. 오케스트레이터가 자동으로 부를 수 있습니다.
  꼭 필요하면 "초안 생성"까지만 하는 기능으로 만드세요.
- 비밀번호, 토큰, 사내 주소를 코드에 적지 마세요. 환경변수로 받으세요.

## 4. 앱스토어 등록 정보

| 항목 | 필수 | 설명 |
|---|---|---|
| `slug` | ✅ | 앱 고유 ID. 영문 소문자와 `-`. 예) `rag-policy` |
| `name` | ✅ | 사람이 보는 앱 이름 |
| `endpoint` | ✅ | 어댑터 주소. 예) `http://my-app:9001/mcp` |
| `usage_hint` | 권장 | **언제 이 앱을 쓰는지** 한 문장. 오케스트레이터가 앱을 고르는 기준 |
| `capability_tag` | 권장 | 역할 태그. 같은 일을 하는 앱끼리 같은 값. 예) `사내규정검색` |
| `owner` / `owner_dept` / `owner_contact` | 권장 | 등록자 이름·소속·연락처. 앱이 고장났을 때 연락처 |
| `description` | | 상세 설명 |
| `category` | | 분류. 예) `hr`, `문서`, `검색` |
| `icon` | | 이모지 하나 |
| `auth_headers` | | 사내 인증이 필요할 때 붙일 헤더 |

## 5. 앱 등급과 승인

| 등급 | 누가 쓸 수 있나 |
|---|---|
| `private` (개인용) | 올린 사람만. 등록하면 처음엔 전부 여기서 시작합니다 |
| `pending` (승인 대기) | 올린 사람만. 관리자 검토 대기 중 |
| `approved` (공식) | 모두 |

오케스트레이터가 부를 수 있는 앱은 **공식 앱 전부 + 요청한 본인이 올린 개인용 앱**입니다.
남이 올린 개인용 앱은 절대 불리지 않습니다.

## 6. 역할이 겹치는 앱 정리 규칙

사내규정 검색 앱이 공식 앱 A 와 어떤 사용자의 개인 앱 B 로 두 개 있으면,
둘 다 불려서 서로 다른 답이 나오면 곤란합니다. 그래서 `capability_tag` 가
같은 앱끼리는 아래 우선순위로 **딱 하나만** 씁니다.

1. 사용자가 요청문에 앱 이름을 직접 적은 앱
2. 사용자가 자기 카드에 넣어 둔 앱
3. 사용자 본인이 올린 개인용 앱
4. 관리자가 승인한 공식 앱

태그가 비어 있거나 서로 다르면 경쟁 관계가 아니므로 전부 후보로 둡니다.

구현: `backend/app/orchestrator/engine.py` 의 `pick_apps()`

## 7. 활용도 집계

앱이 불릴 때마다 성공/실패, 걸린 시간, 누가 썼는지가 기록됩니다
(`app_call_logs` 테이블). `GET /api/stats/apps` 가 월별 순위를 돌려줍니다.

순위는 단순 호출 수가 아니라 **성공한 호출 수** 기준입니다. 많이 불렸지만
계속 실패한 앱이 1등이 되면 안 되기 때문입니다. 성공률과 실제 사용자 수도
함께 나옵니다.
